# 联网补洞：给已有材料的缺口挂上真实来源

Status: 设计已确认（经两轮实测收窄），待出实施计划
Date: 2026-07-27

## 1. 要解决什么

用户已导入课件/PDF，权威口径在手，但材料里某些知识点**只提了名字没展开**——术语没定义、公式没说适用条件、结论没给前提。用户选中这些缺口，系统联网找解释，产出一份可审阅的 Markdown，用户决定是否并入材料。

**只做补洞。不做「从零生成」。** 原设计包含「只给一个主题、系统搜出一整份小抄」的模式，实测后删除（依据见第 8 节）。

从零的需求由**组合**满足，不做成独立模式：用现有的 `/api/ai/structurize` 或对话让 AI 起一份草稿骨架 → 再用本功能给骨架上的缺口挂真实来源。这条路径的第一步是模型凭记忆生成，但那是用户主动要求、明确知情的，与第 2 节禁止的「静默退化」性质不同——区别在透明，不在是否用了模型知识。

## 2. 不可谈判的约束

这些内容最终会印在用户带进考场的纸上。

- **网上内容不等于本课口径。** 不同教材符号约定不同，老师的定义可能更窄。抓回的内容一律是候选，必须经用户确认才进正文。
- **只重组不新增。** 总结沿用 `/api/ai/structurize` 的既有约束：只压缩重组搜索结果说过的话，不补充模型自己的知识。
- **搜索不可用时明确失败。** 绝不退化成让模型凭记忆写一段——这是本功能最危险的失败模式，因为产出看起来完全正常。第 8 节记录了这个失败模式的真实样本。
- **每一节都带出处 URL。** 用户考前要能判断哪些是课件原文、哪些是网上来的，并能回查。

## 3. 流水线

```
用户在 KnowledgeIR 节点列表里勾选缺口节点
            │
            ▼
   前端取节点文字（截断 60 字）填进查询框，用户可改写
            │
            ▼
   SearchProvider.search(query, 10)
            │  → { title, snippet, url, publishDate }[]
            ▼
   质量闸（source-quality.ts，纯函数）
     · 黑名单域名剔除
     · 同源去重（实测 10 条里 4 条来自同一站）
     · 域名加权排序
            │
            ▼
   取前 4 条 snippet（不抓原页，理由见下）
            │
            ▼
   一次模型调用：4 段 snippet → 一份按源分节的 Markdown
            │
            ▼
   一张候选卡（enabled=false），用户可删节、改写、勾选启用
```

### v1 不抓原页

实测智谱 `web_search` 返回的 `content` 字段平均 574 字（样本 227–703），是搜索引擎已抽好的正文片段。对「解释一个术语」这个目标，这个长度够用。

代价与取舍：

- snippet **全部在句子中间截断**，会丢掉解释的尾巴。补洞只要一段说明，可接受。
- snippet **带噪声**（博客开场白、残留 HTML 标签）。由总结环节吸收，不直接展示给用户。
- 因此 v1 **不发起任何外部 HTTP 请求**，整个 SSRF 面、超时、大小限制、并发抓取都不存在。

需要深度时再加「抓原文」的单源动作——`importUrl` 已经就绪，加它是纯增量，不改本设计。

### 漏斗 10 → 4

搜索单次固定返回 10 条。取 4 是因为瓶颈在用户要读，不在服务器。一个术语给 4 个来源足够交叉验证，再多会退化成「全选」，等于没把关。

### 产出形状

**一份** Markdown，内部按源分节：

```markdown
## 戴维南定理的适用条件

### 来自 zhuanlan.zhihu.com
（该源内容的总结）

> https://zhuanlan.zhihu.com/p/...

### 来自 m.elecfans.com
（该源内容的总结）

> https://m.elecfans.com/...
```

分节而非合成一段，是为了保住溯源。四节讲同一件事时重复是可见的——用户直接删掉三节，人工判断替代自动去重。

## 4. 模块边界

| 模块 | 职责 | 依赖 |
|---|---|---|
| `SearchProvider`（接口） | `search(query, limit) → SearchHit[]` | 无 |
| `ZhipuSearchProvider` | 智谱 `web_search`，**本期主实现** | 现有 `ai-provider` 的白名单与 BYOK |
| `BraveSearchProvider` | 备选适配器，**本期只留接口不实现** | 无 |
| `source-quality.ts` | 黑名单、同源去重、域名加权 | 纯函数 |
| `research-pipeline.ts` | 串联搜索→筛→总结，产出 `ImportedDocument` | 上述 + `ai-structurize` |
| `routes/research.ts` | `POST /api/research/jobs` | pipeline + `import-job-store` |

`source-quality.ts` 是唯一需要密集单测的地方，且全是纯函数。

### 复用 import-job 队列

研究任务的产出是 `{ markdown, summary }`，与 `ImportedDocument` 同形。给 `ImportedDocumentKind` 加一个 `'research'`，队列**无需泛型化**即可复用，白拿：阶段进度、主动取消、并发闸与配额（429 背压）、落盘持久化、7 天保留、重启恢复、最近任务列表。

`DocumentImportSummary` 增加可选字段 `sources?: { url: string; domain: string; title: string }[]`，承载本次采纳的来源清单。

## 5. 接口

### `POST /api/research/jobs`

```ts
{
  query: string;                  // 最终查询词，前端从节点派生、用户可改
  provider?: AiProviderConfig;    // BYOK，缺省用服务器 key
}
```

返回 `202` + 任务快照。**只新增提交端点**：查进度 / 取详情 / 取消 / 列历史全部直接用既有的 `GET|DELETE /api/import/jobs/:jobId` 与 `GET /api/import/jobs`——两类任务共用同一个 job store，在同一条队列里排队、共享并发额度。前端靠 `summary.kind === 'research'` 区分卡片形态。

## 6. 失败与降级

| 情况 | 行为 |
|---|---|
| 搜索返回 0 条 | `422 RESEARCH_NO_RESULTS`，提示换关键词。**不让模型凭记忆编** |
| 搜索 key 未配 / 无权限 | `501 RESEARCH_UNAVAILABLE`，明确说明缺什么 |
| 质量闸筛完不足 4 条 | 有几条用几条，卡片注明「符合质量要求的只有 N 个源」 |
| 质量闸筛完为 0 | `422 RESEARCH_ALL_FILTERED`，附被过滤的域名列表——让用户知道是被拦了，不是没搜到 |
| 总结阶段模型不可用 | `502`，并在错误里附上已搜到的标题与 URL 清单，用户至少能自己去看 |
| 用户取消 | 沿用 job store 的 cancelled 语义 |

## 8. 选型验证记录（2026-07-27 实测）

### DeepSeek 不具备联网，且失败是静默的

| 试法 | 结果 |
|---|---|
| `enable_search: true` | **HTTP 200，参数被静默忽略**。message 只有 `role`/`content`，无引用字段；模型自述知识截止 2025-05 |
| `tools: [{type:"web_search"}]` | HTTP 400，`unknown variant 'web_search', expected 'function'` |

第一条是第 2 节所述最危险失败模式的真实样本：接口 200、格式正确、内容读着像模像样，但一个字都不来自网络。**若未经验证就实现，产出会静默退化成模型编造，而用户会把它打印出来带进考场。**

### 智谱 `web_search` 可用，但索引质量决定了功能边界

用「戴维南定理 等效电路 适用条件」实测：

- 单次固定 10 条，**10/10 全部带 `link`**，另有 `publish_date`。溯源硬要求满足。
- `content` 平均 574 字，已是抽好的正文片段。
- **`search_std` 与 `search_pro` 返回完全相同**——付费档在此查询上无增益。
- `search_pro_quark` 换成文库站（book118 / 人人文库 / 百度文库）与百度知道，多有付费墙或登录墙，更差。

域名分布（search_std）：

```
4×  wenwen.sogou.com      ← 问答农场，占 40%
1×  baijiahao.baidu.com   ← 百家号
1×  k.sina.cn      1×  www.aitaocui.cn
1×  ispacesoft.com 1×  www.mrchip.cn   1×  m.elecfans.com
```

**零个 .edu.cn、零个维基、零个教材源。** 查询词工程也无效：`site:edu.cn` 被忽略，加「维基百科」搜不出维基，加「大学讲义课件」只多出付费墙文库站。

### 这个发现如何收窄了范围

索引里没有学术源，加权只能排序不能凭空创造。因此：

- **「从零」模式删除。** 手里没有权威材料、全靠消费级网页拼一份完整小抄带进考场，风险不可接受，且这是搜索源的限制而非实现的限制——质量闸、重排、总结都改善不了「库里没有好东西」。
- **「补洞」保留。** 用户已有权威口径，只要一段通俗解释，消费级内容够用；实测那几段戴维南定理的描述内容本身没有错误。

### 黑名单初始清单

依据实测样本，先硬编码这些（后续按真实使用迭代）：

```
wenwen.sogou.com    zhidao.baidu.com    baijiahao.baidu.com
max.book118.com     m.renrendoc.com     wk.baidu.com        doc.wendoc.com
```

保留知乎专栏、专业社区（elecfans 等）与个人博客——中文复习资料的好内容大量在这些地方。

## 9. 测试

**单元（纯函数，无网络）**
- 黑名单命中与放行
- 同源去重：同一站的多条只保留权重最高的一条
- 域名加权排序
- 分节 Markdown 组装：每节都带 URL
- **回归锁**：搜索返回 0 条时，断言未调用总结模型（防静默退化，对应第 2 节红线）

**集成（打桩 SearchProvider）**
- 4 源正常 → 一份四节文档
- 筛完剩 1 条 → 一节文档 + 「只有 1 个源」提示
- 筛完为 0 → `RESEARCH_ALL_FILTERED` 且附域名列表
- 取消 → 中途 abort，不产出部分结果

**真实联网**：不进 CI。提供 `pnpm bench:research -- "<查询词>"`，输出各阶段耗时、通过质量闸的域名、最终分节文档，供人工判断质量。

## 10. 本期不做

- 抓原页（`importUrl` 已就绪，需要深度时作为单源动作增量接入）
- `BraveSearchProvider` 的实际实现
- 黑白名单的用户自定义 UI（先硬编码，观察真实使用后再决定是否暴露）
- 图片
- 跨轮次检索历史与增量补搜
- 自动判断「该联网了」——永远由用户主动触发

## 11. 其余已知风险

- **总结环节仍是模型。** 「只重组不新增」靠 prompt 约束，不是硬保证。这是必须保留原文 URL、让用户能回查的原因。
- **搜索质量无法在 CI 里回归。** 单测只覆盖质量闸的纯函数；「搜出来的东西好不好」只能靠 `bench:research` 人工看。
- **黑名单是打地鼠。** 中文内容农场的 SEO 长期优于正经资料，初始清单必然不全，需按真实使用迭代。
- **snippet 截断会丢解释的尾巴。** 若实际使用中发现总结经常缺关键结论，就是该接「抓原文」的信号。
