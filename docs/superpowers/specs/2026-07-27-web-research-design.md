# 联网检索material：自动搜索并抓取网页作为排版材料

Status: 设计已确认，待出实施计划
Date: 2026-07-27

## 1. 要解决什么

用户手上的材料不总是够。两种时刻：

- **从零**：只有一个主题（「电磁学期末」），手里没有课件。
- **补洞**：已导入课件/PDF，但某些知识点只提了名字没展开。

现在仓库只有「用户给一个 URL → 抓取正文」（`POST /api/import/url`），没有任何搜索能力。本功能补上搜索这一环，并把抓回的内容变成**可审阅、可拒绝**的材料。

**模式由用户主动选，不自动触发。** 系统永远不会因为「觉得材料不够」就自己去联网。

## 2. 不可谈判的约束

这些内容最终会印在用户带进考场的纸上，因此：

- **网上内容不等于本课口径。** 不同教材符号约定不同，老师的定义可能更窄。抓回的内容一律是候选，必须经用户确认才进正文。
- **只重组不新增。** 总结阶段沿用 `/api/ai/structurize` 的既有约束：只压缩重组网页说过的话，不补充模型自己的知识。
- **搜索不可用时明确失败。** 绝不退化成「让模型凭记忆写一段」——这是本功能最危险的失败模式，因为产出看起来完全正常。
- **每一节都带出处。** 用户考前要能判断哪些是课件原文、哪些是网上抓的。

## 3. 流水线

```
用户选模式
 ├─ 从零：输入主题 ──────────────→ 查询词
 └─ 补洞：从 KnowledgeIR 挑节点 ─→ 查询词
                                    │
                    SearchProvider.search(query, 10)
                                    │  → { title, snippet, url }[]
                    质量闸（source-quality.ts，纯函数）
                      · 黑名单域名剔除
                      · 同源去重（中文互联网转载极多）
                      · 域名加权（.edu.cn / 维基 / 出版社 / 开放课程靠前）
                                    │
                    模型按查询词对剩余摘要重排 → 取前 4
                      （摘要阶段筛比抓完再筛便宜一个量级）
                                    │
                    并发 fetch × 4 —— 复用现有 importUrl
                      （SSRF 防护 / 15s 超时 / 5MB 上限 / 重定向逐跳复查全部白捡）
                                    │
                    Readability 抽正文，正文 < 400 字丢弃（不占名额，也不补位）
                                    │
                    逐源 AI 总结 → 合并成一份 Markdown，按源分节
                                    │
                    一张候选卡（enabled=false）
                                    │
                    用户审阅、可删节、勾选后并入材料
```

### 漏斗宽度：10 → 4 → 4

瓶颈不是服务器（抓取是 I/O 密集，可并发），**是用户要读**。10 分钟的产品目标下，4 节内容读得完；8 节会退化成「全选」，等于没把关。

### 产出形状

**一份** Markdown 文档，内部按源分节：

```markdown
## 高斯定律 · 来自 zh.wikipedia.org

（该源内容的总结）

> 来源：https://zh.wikipedia.org/wiki/...

## 高斯定律 · 来自 phys.xxx.edu.cn

（该源内容的总结）

> 来源：https://phys.xxx.edu.cn/...
```

分节而非合并成一段，是为了保住溯源。四节讲同一件事时重复是可见的——用户直接删掉三节，人工判断替代了自动去重。

## 4. 模块边界

| 模块 | 职责 | 依赖 |
|---|---|---|
| `SearchProvider`（接口） | `search(query, limit) → SearchHit[]` | 无 |
| `ZhipuSearchProvider` | 智谱 `web_search` 接口，**本期主实现** | 现有 `ai-provider` 的白名单与 BYOK |
| `BraveSearchProvider` | Brave 适配器，**本期只留接口不实现** | 无 |
| `source-quality.ts` | 黑名单、同源去重、域名加权、正文门槛 | 纯函数 |
| `research-pipeline.ts` | 串联搜索→筛→抓→总结，产出 `ImportedDocument` | 上述 + `importUrl` + `ai-structurize` |
| `routes/research.ts` | `POST /api/research/jobs` 等 | pipeline + `import-job-store` |

`source-quality.ts` 是唯一需要密集单测的地方，且全是纯函数：黑名单命中、转载去重、加权排序、正文门槛。

### 为什么能复用 import-job 队列

研究任务的产出是 `{ markdown, summary }`，与 `ImportedDocument` 同形。给 `ImportedDocumentKind` 加一个 `'research'`，队列**无需泛型化**即可复用，白拿：

- 阶段进度与文案（searching / fetching / summarizing）
- 主动取消（`AbortSignal` 一路传到 fetch 和模型调用）
- 全局并发闸与单用户配额（429 背压）
- 落盘持久化、7 天保留、重启恢复、最近任务列表

`DocumentImportSummary` 增加可选字段 `sources?: { url: string; domain: string; title: string }[]`，承载本次采纳的来源清单。

## 5. 接口

### `POST /api/research/jobs`

```ts
{
  mode: 'topic' | 'gap';
  query: string;           // 最终用于搜索的查询词，两种模式都必填
  provider?: AiProviderConfig;   // BYOK，缺省用服务器 key
}
```

**gap 模式的查询词由前端派生、用户可改。** 用户在 KnowledgeIR 节点列表里勾选缺口节点，前端取节点 `text`（截断到 60 字）填进查询框，用户确认或改写后再提交。服务端只收最终查询词，不做节点解析——这样「搜什么」始终对用户可见可改，也避免服务端依赖前端持有的知识文档。

**只新增提交端点，不新增查询端点。** 研究任务与导入任务共用同一个 job store，因此：

- 提交：`POST /api/research/jobs` → `202` + 任务快照（与导入同形）
- 查进度 / 取详情 / 取消 / 列历史：直接用既有的 `GET|DELETE /api/import/jobs/:jobId` 与 `GET /api/import/jobs`

两类任务在同一条队列里排队、共享并发额度——它们抢的是同一份 CPU 和内存。前端靠 `summary.kind === 'research'` 区分卡片形态。

## 6. 失败与降级

| 情况 | 行为 |
|---|---|
| 搜索返回 0 条 | `422 RESEARCH_NO_RESULTS`，提示换关键词。**不让模型凭记忆编** |
| 联网能力不可用（模型不支持/未配 key） | `501 RESEARCH_UNAVAILABLE`，明确说明原因 |
| 质量闸筛完不足 4 个 | 有几个用几个，卡片注明「符合质量要求的只有 N 个源」 |
| 4 个源挂了 3 个 | 返回活着的 1 个 + 列出失败的 URL 与原因，不假装成功 |
| 全部抓取失败 | `502 RESEARCH_FETCH_FAILED`，附各源失败原因 |
| 总结阶段模型不可用 | 退回展示 Readability 抽出的正文前 N 字，该节标注「未总结·原文摘录」 |
| 用户取消 | 沿用 job store 的 cancelled 语义，已抓内容丢弃 |

## 8. 测试

**单元（纯函数，无网络）**
- 黑名单命中与放行
- 同源去重：同一篇文章在三个域名下只保留权重最高的
- 域名加权排序：`.edu.cn` 排在内容农场之前
- 正文门槛：< 400 字被丢弃且不补位
- 分节 Markdown 组装：每节都带 URL

**集成（打桩 SearchProvider 与 fetch）**
- 4 源全成功 → 一份四节文档
- 3 源失败 → 一节文档 + 失败清单
- 搜索 0 结果 → 明确错误码，且**断言没有调用模型生成内容**（防退化的回归锁）
- 取消 → 中途 abort，不产出部分结果

**真实联网**：不进 CI（不稳定、要 key）。提供 `pnpm bench:research -- "<主题>"` 手动跑，输出各阶段耗时与最终来源清单。

## 10. 搜索源的选型验证（2026-07-27 实测）

设计初稿原本打算「先用模型内置联网走通」。动手前先验了一轮，结论推翻了这个选择，故记录在案。

**DeepSeek 完全不具备联网能力，且失败方式是静默的：**

| 试法 | 结果 |
|---|---|
| `enable_search: true`（通义风格参数） | **HTTP 200，参数被静默忽略**。响应 message 只有 `role`/`content` 两个字段，无任何引用信息；模型自述知识截止 2025-05 |
| `tools: [{type:"web_search"}]` | HTTP 400，`unknown variant 'web_search', expected 'function'` |

第一条是本功能最危险的失败模式的真实样本：**接口 200、格式完全正确、内容读起来也像模像样，但一个字都不来自网络**。若未经验证就基于「传 `enable_search` 就能联网」实现，产出会静默退化成模型凭记忆编造，而用户会把它打印出来带进考场。

**因此改用智谱 `web_search` 独立接口作为主实现。** 理由：

- 是纯搜索接口而非「带搜索的对话」，返回结构化结果**必然带 URL**——溯源是硬要求，这一点不能赌。
- 中文覆盖好。本产品的材料是中文课程资料，英文索引为主的搜索源（Brave/Serper）在「戴维南定理」「剩余价值率」这类查询上质量明显偏低。
- `open.bigmodel.cn` 已在 `ALLOWED_HOSTS` 白名单内，无需改动安全配置。
- 一把 key 同时服务两步：搜索用 `web_search`，分节总结用 `glm-4-flash`。

**前置条件**：需要一把智谱 key。开工前应先按同样方式实测一次 `web_search` 的真实返回结构（确认字段名、是否稳定带 URL、单次返回条数上限），再据此定 `SearchHit` 的映射。

## 11. 其余已知风险

- **中文内容农场的 SEO 常优于正经资料。** 黑名单 + 域名加权只能缓解，不能根治。真实使用后需按实际结果迭代黑名单。
- **总结环节仍是模型。** 「只重组不新增」靠 prompt 约束，不是硬保证。这也是必须保留原文 URL、让用户能回查的原因。
- **搜索质量无法在 CI 里回归。** 单测只能覆盖质量闸的纯函数部分；「搜出来的东西好不好」只能靠 `bench:research` 人工看。
